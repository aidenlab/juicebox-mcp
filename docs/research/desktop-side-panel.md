# Showing the viewer in the desktop side panel: Claude Desktop and ChatGPT Desktop (macOS)

Researched 2026-10-16 from primary sources only. Each claim cites its source and the version or date it was read at. **[inferred]** marks a conclusion drawn from the sources that they do not state. **[unverified]** marks a behaviour that needs a hands-on test.

Goal: on both desktop apps the Hi-C viewer (`https://juicebot-dev.3dg.io/?room=<id>`) opens in the side panel beside the conversation by itself, with a button only as a fallback.

## Short answer

## 1. A browser tool in the desktop app

### Claude Desktop

- **What it is and where it shows.** "When a Cowork task involves a website, a browser opens in the side panel next to your task. Claude opens sites, reads pages, clicks, types, and fills forms while you watch … Links in the task transcript open in the same panel." ([support.claude.com 16607400](https://support.claude.com/en/articles/16607400-use-the-built-in-browser-in-claude-cowork), "Updated this week", read 2026-10-16)
- **Availability.** "rolling out gradually this week to Cowork in Claude Desktop for macOS, Windows, and Linux (beta) on Pro, Max, and Team plans, and on Enterprise plans where an owner has enabled it." The article adds a note that "Claude Cowork is now just Claude", and that Chat and Cowork are being unified (rollout to Pro and Max, beta for Enterprise). (same source)
- **Which browser the model uses.** Settings › Cowork › **Preferred browser**: built-in or Claude in Chrome. Existing Claude in Chrome users keep Chrome as the default. (same source)
- **Site approval.** "Claude asks for your permission before acting on a site for the first time." The 3P admin doc names the choices: "**Allow once** covers that page, and **Always allow** saves the site on the device until the user revokes it in **Settings**." ([claude.com/docs third-party/claude-desktop/browser](https://claude.com/docs/third-party/claude-desktop/browser.md), read 2026-10-16) That page also scopes the pane to "Cowork and Code sessions" and says it is off by default for 3P deployments (`builtinBrowserEnabled`).
- **Tool names.** In the desktop app the model sees tools named `mcp__Claude_Browser__*`. Before they are turned on, a single `enable__…Claude_Browser` tool may stand in for them. Source: this session's own tool and skill listing, not a public document. **[unverified as a public contract]**
- **Can our tool result make the model use it?** No document says so. Anthropic's directory review rejects tool descriptions that "Instruct Claude to call external software or tools the user didn't request" ([review-criteria](https://claude.com/docs/connectors/building/review-criteria.md), read 2026-10-16). That rule covers descriptions. **[inferred]** A tool result that asks the model to open the join link in the browser is plausible for a custom connector, but it is the model's choice each time, and wording it as an instruction risks failing directory review. Phrase it as a fact the user asked for ("the viewer for this room is at …; the user wants to see it").

### ChatGPT Desktop

- **What it is.** "The built-in browser in the ChatGPT desktop app gives you and ChatGPT a shared view of websites and local web apps inside a chat." Users can "**Enter split view** to show the chat and tab side by side", "open a URL from the chat", or press ⌘T. ([learn.chatgpt.com/docs/browser](https://learn.chatgpt.com/docs/browser.md), read 2026-10-16)
- **Model control is limited to Work and Codex.** "In the desktop app, Computer Use lets ChatGPT Work or Codex operate the built-in browser directly … Browser is included with the desktop app and installs automatically. Ask ChatGPT or Codex to use the built-in browser in your task, or reference it directly with `@Browser`." (same source) Setup: in the desktop app, choose ChatGPT › **Work** (or Codex), then Plugins › Computer Use › Install/Enable ([learn.chatgpt.com/docs/computer-use](https://learn.chatgpt.com/docs/computer-use.md), read 2026-10-16). The desktop app's composer has a Chat/Work toggle ([learn.chatgpt.com/docs/app](https://learn.chatgpt.com/docs/app.md)). **[inferred]** In plain Chat the model has no tool for opening a URL in the pane.
- **Approval.** "In **Settings > Browser > Agent permissions**, choose default permissions for browsing … and add exceptions for specific websites." (browser doc)
- **Influence from a tool result.** OpenAI's plugin guidelines: "Do not instruct the model to invoke another plugin or connector to complete its operation", and model-readable fields must not "manipulate how the model selects or uses other plugins" ([developers.openai.com/plugins llms-full](https://developers.openai.com/plugins/llms-full.txt), Plugin guidelines, read 2026-10-16). Steering the model to `@Browser` from our tool result therefore conflicts with directory review. **[inferred]**
- **Atlas, the separate OpenAI browser app, is not ChatGPT Desktop and was not researched.**

## 2. MCP Apps and Apps SDK: display modes, open-link, defaults

### The standard (ext-apps)

- Display modes are `"inline" | "fullscreen" | "pip"`: "fullscreen: View takes over the full screen/window", "pip: Picture-in-picture, floating overlay". **There is no panel or side mode.** The view requests a change with `ui/request-display-mode`, the host "MUST return the resulting mode", and it may decline. ([ext-apps specification/draft/apps.mdx](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/draft/apps.mdx), commit 82221c0 of 2026-09-25, package v2.0.3; the stable 2026-01-26 spec is the same)
- `ui/open-link`: "Host SHOULD open the URL in the user's default browser or a new tab". The error example is "Link opening denied by user". The spec states no user-gesture rule. (same)
- **No tool-level metadata in the standard picks a display mode or a panel.** Tool `_meta.ui` carries only `resourceUri` and `visibility`. (same)

### Claude

- Docs: "An MCP App appears in the conversation as an inline card, an inline carousel, or a full screen view." In full screen "the composer remains available" and "a close button appears in the native header bar". The modes listed for `ui/request-display-mode` are `inline`, `fullscreen` and `pip`. ([design-guidelines](https://claude.com/docs/connectors/building/mcp-apps/design-guidelines), read 2026-10-16) Full screen replaces the conversation view rather than sitting beside it, and Claude documents no side-panel placement for MCP Apps.
- `pip` on claude.ai answers `{"mode":"inline"}`. The issue is open, and maintainer ochafik replied on 2026-04-21 that a view should check `availableDisplayModes` first ([anthropics/claude-ai-mcp#60](https://github.com/anthropics/claude-ai-mcp/issues/60), opened 2026-02-17). Desktop was not tested in that issue.
- Open-link: "When your MCP App sends a `ui/open-link` request, Claude shows an **Open external link** confirmation modal … If the user confirms, the link opens in a new tab." The modal is skipped only for a **directory** connector, a destination on its "Allowed link URIs" list, **and** a "real user gesture". "Custom connectors and locally configured servers always show it." Without a gesture, "Claude shows the modal so the user's confirmation click supplies the gesture." ([external-links](https://claude.com/docs/connectors/building/mcp-apps/external-links.md), read 2026-10-16) This matches the earlier note in `juiceboxView.js` (a prompt, then the external browser). The docs do not say whether "a new tab" means the built-in browser panel in Cowork. **[unverified]**
- Nothing in Claude's docs lets a server open its view fullscreen by default. **[unverified]** whether `ui/request-display-mode {mode:"fullscreen"}` is honoured without a gesture on arrival. Even if it is, it would cover the conversation rather than sit beside it.

### ChatGPT (Apps SDK, now "Plugins", plus OpenAI MCP Extensions)

- Modes: "ChatGPT supports `inline` and `fullscreen`, but not `pip`." Resource-level `_meta["openai/ui"]` takes `availableDisplayModes` and `preferredDisplayMode`. "When the model invokes an MCP App, ChatGPT considers `preferredDisplayMode` when choosing the initial display mode." "If `availableDisplayModes` includes both `inline` and `fullscreen`, ChatGPT defaults to `fullscreen` unless `preferredDisplayMode` specifies otherwise. On Desktop, if `availableDisplayModes` is omitted, ChatGPT defaults to `inline`." ([openai/mcp-extensions docs/spec.md §Display Modes](https://github.com/openai/mcp-extensions/blob/main/docs/spec.md), commit 0d60621 of 2026-10-09, changelog 0.2.0 of 2026-10-10) The Plugins docs agree: `availableDisplayModes: ["fullscreen"]` "lets ChatGPT open it in fullscreen immediately, without showing an inline loading state first" ([Plugins reference](https://developers.openai.com/plugins/llms-full.txt), read 2026-10-16). **This is the one documented server-side switch that opens a view large without a click.**
- **Side panel (OpenAI extension).** "Conversation panels: Let users open your app beside a conversation" means `_meta["openai/ui"].entrypoints: [{type: "thread"}]` on the tool, which adds "an entrypoint in a conversation's side panel" (Plugins › Plugin Extensions). In the spec: "Thread entrypoints let users **manually** open an MCP App as a new content tab within a thread", the server receives `{}` as arguments, "ChatGPT uses `fullscreen` for all entrypoints", and "On desktop, global entrypoints open with a composer and thread layout, with the app as a permanent tab." Platform table: thread entrypoint and display modes are "Supported" on Desktop. Caveat: "Classic ChatGPT is excluded", and the table "describes expected support at DevDay launch". (spec §Platform Support, §Thread Entrypoint)
- **[unverified]** Whether a *model-invoked* fullscreen app on ChatGPT Desktop renders as a side-panel tab beside the thread or as a full overlay. The docs describe fullscreen generically ("The ChatGPT composer remains overlaid", Plugins UI guidelines) and the side-panel tab only for entrypoints.
- `window.openai.requestDisplayMode({mode})` requests inline, PiP or fullscreen ("On mobile, picture-in-picture may be presented as fullscreen"). `window.openai.openExternal({href})` will "Open a vetted external link in the user's browser", with trusted targets in `_meta["openai/widgetCSP"].redirect_domains`. (Plugins reference) No gesture rule is documented for either, and no route into the built-in browser.

## 3. Sandbox and CSP in each host

- **Standard.** `connectDomains` covers "fetch/XHR/WebSocket" (the example includes `wss://realtime.service.com`). `resourceDomains` covers scripts, images, styles, fonts and media, with wildcard subdomains (`https://*.example.com`). If `frameDomains` is omitted, the policy is `frame-src 'none'`. The default CSP has `connect-src 'none'`. (ext-apps draft spec, v2.0.3)
- **Claude.** "All external origins are blocked by default. Declare the origins each `ui://` resource needs through `_meta.ui.csp`" (connectDomains, resourceDomains, baseUriDomains). "The `frameDomains` field, for embedding third-party iframes, is restricted in Claude pending security review." (design-guidelines, read 2026-10-16) So `juiceboxView.js`'s finding (no framing other origins) still holds. The docs show no relaxation. App requests carry `Origin: {sha256(serverUrl)[:32]}.claudemcpcontent.com` ([troubleshooting](https://claude.com/docs/connectors/building/mcp-apps/troubleshooting.md), [getting-started §ui.domain](https://claude.com/docs/connectors/building/mcp-apps/getting-started.md)).
- **ChatGPT.** "Nested frames are blocked by default", "Plugins can embed pages from their MCP server's own registrable domain … Separate tenants on a shared hosting service count as different domains." Each origin goes in `_meta.ui.csp.frameDomains` (or the legacy `openai/widgetCSP.frame_domains`). "You must still provide a justification when submitting a plugin that uses iframes … may lead to slower approval or rejection." Importantly: "An embedded page uses its own CSP; the widget `connectDomains` and `resourceDomains` allowlists do not restrict network requests made inside that page." (Plugins: CSP, Network access, Plugin guidelines › Iframes, read 2026-10-16)
- **What this means for Juicebox [inferred]:**
  - *Iframe the viewer page* (ChatGPT only): declare `frameDomains: ["https://juicebot-dev.3dg.io"]`. The page then opens its own `wss://juicebot-mcp-dev.3dg.io` socket and fetches `.hic` files from any host under its own CSP, so no per-host allow-list is needed. Its WebSocket `Origin` stays `https://juicebot-dev.3dg.io`, which is already on `ALLOWED_ORIGINS`. Custom-connector (developer mode) use needs no review. A directory listing needs the iframe justification.
  - *Bundle juicebox.js into the view* (both hosts): `connectDomains` must list `wss://juicebot-mcp-dev.3dg.io` and every `.hic` host (`https://hicfiles.s3.amazonaws.com`, `https://www.encodeproject.org`, 4DN's hosts, plus whatever redirect targets they use). Arbitrary user-supplied URLs fail unless they are listed, since wildcards cover only subdomains. Each data host must also answer CORS for the sandbox origin **[unverified per host]**. The Worker's `ALLOWED_ORIGINS` would have to admit the sandbox origin (`<hash>.claudemcpcontent.com` for Claude; ChatGPT's sandbox origin is undocumented here).

## 4. Conclusion per host

- **Claude Desktop: (i) the model calls the built-in browser, or else (iii).** No MCP App route reaches a side panel. There is no panel display mode, framing another origin is forbidden, and a gestureless `ui/open-link` from a custom connector always shows a modal and then opens a tab. In a **Cowork** (or unified "Claude") session with the built-in browser rolled out, the model can open the join link in the side panel itself. The user approves the site once (Always allow) and later opens need no click. In a plain Chat conversation, or where the browser is not rolled out or is disabled by the org, the card's **Open Juicebox** button is the way in (iii). A Cowork transcript link also opens in the panel, on a click.
- **ChatGPT Desktop: (ii) the view embeds the viewer, or else (i) in Work mode.** Set `_meta["openai/ui"] = {availableDisplayModes: ["inline","fullscreen"], preferredDisplayMode: "fullscreen"}` on the resource. Then ChatGPT opens the view fullscreen with no click when the model calls `get_juicebox_url`. Have the view iframe `https://juicebot-dev.3dg.io/?room=<id>` (`frameDomains`, same registrable domain `3dg.io`). Also add a `{type:"thread"}` entrypoint so the user can open the viewer in the side panel. Whether model-invoked fullscreen on desktop is the side-panel tab or a full overlay is the key **[unverified]** point. In Work mode, the model can instead open the link in the built-in browser's split view (`@Browser`), subject to agent site permissions.
